# Git Commit Message Convention

## 형식

```
타입: 무엇을 했는지 (한글)
```

예시

```
feat: 여행 목록 화면 추가          ← 프론트
feat: 여행 생성 API 추가           ← 백엔드
fix: 정산 화면에서 금액이 잘리는 문제 수정
docs: 브랜치 컨벤션 정리
```

프론트인지 백엔드인지는 따로 적지 않습니다. PR의 **구분** 체크박스와 바뀐 파일 경로(`lib/` / `backend/`)로 알 수 있습니다.

## 타입 (6개만 기억하기)

타입은 **영어 소문자**로 쓴다. 브랜치 이름 앞에 붙이는 단어와 같다.

| 타입 | 언제 |
|---|---|
| `feat` | 새 기능 추가 |
| `fix` | 버그 수정 (급한 버그 포함) |
| `docs` | 문서 수정 |
| `refactor` | 동작은 그대로, 코드 구조만 개선 (이름 변경·파일 이동·삭제 포함) |
| `test` | 테스트 추가·수정 |
| `chore` | 그 외 전부 (설정, 의존성 `pubspec.yaml` · `build.gradle.kts`, 포맷 정리, `.gitignore` 등) |

어느 타입인지 헷갈리면 `chore`를 쓴다. 타입 때문에 고민하는 시간이 더 아깝다.

## 규칙

1. 제목은 **한글**로, 무엇을 했는지 한 줄로 쓴다.
2. 제목 끝에 `.`을 붙이지 않는다.
3. 더 설명할 게 있으면 한 줄 띄우고 본문에 **왜** 바꿨는지 쓴다. (선택)
4. 한 커밋에는 한 가지 변경만 담는다.

> 커밋 메시지가 조금 틀려도 괜찮습니다. PR을 **Squash merge**로 합치면 `main`에는 PR 제목 하나만 커밋으로 남습니다. 그래서 **PR 제목만 이 규칙을 지키면 됩니다.**

## 본문까지 쓰고 싶을 때

```bash
git commit -m "feat: 여행 생성 API 추가" -m "생성자를 여행 멤버로 자동 등록하도록 함"
```

`-m`을 두 번 쓰면 첫 번째가 제목, 두 번째가 본문이 된다.
